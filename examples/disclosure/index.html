Progressive disclosure (experimental)

A fixture with 200 tools and two skills. Measures how many bytes a flat tools/list sends to the model, and checks a plain client and a groups client on both wires.

Source: examples/disclosure/README.md

disclosure: 200 tools and two skills ¶

An agent connects to a server with 200 tools. tools/list sends every schema, and the host puts
all of them into the model’s context, about 82 KB of JSON here. The model may need one billing
tool.

This example serves that situation so you can measure it. The server has 200 tools in eight
themes (billing, deploy, search, users, storage, metrics, alerts, docs) and two SEP-2640 skills.
billing-refunds uses billing tools. incident-triage uses alerts, metrics and deploy tools.

Run it ¶

just serve          # terminal 1: the fixture on :8080
just demo           # terminal 2: the walkthrough

Both sides take --wire=legacy or --wire=stateless.

The walkthrough connects, counts the bytes of the flat tools/list, lists the skills, and reads
billing-refunds with its digest checked. See WALKTHROUGH.md for the steps.

Check mode ¶

--check connects two clients and prints one row per check:

go run . --serve --addr=127.0.0.1:18420 --wire=stateless &
go run . --check --url http://127.0.0.1:18420 --wire=stateless

  PASS stateless plain client: tools/list returns every tool: 200 of 200 tools, 82054 bytes
  PASS stateless plain client: SKILL.md reads and verifies: skill://billing-refunds/SKILL.md, 424 bytes, digest verified true
  FAIL stateless groups client: groups/list returns one group per theme: RPC error -32601: method not found: groups/list
  FAIL stateless groups client: groups/get billing returns its tools and SKILL.md: RPC error -32601: method not found: groups/get
  FAIL stateless groups client: tools/list leaves out grouped tools: 200 of 200 tools, 82054 bytes
  INFO stateless sizes: groups/get billing vs flat tools/list: flat tools/list 82054 bytes, groups/get n/a

The plain client declares no extensions and must get the flat list. The groups client declares
io.modelcontextprotocol/groups, an extension the Progressive Disclosure working group drafts.
mcpkit does not serve it yet, so the groups rows fail and the command exits 1. The last row
prints the size of one group next to the flat list.

Walkthrough

Generated from the scripted demo — run it with make serve + make demo. Source: examples/disclosure/WALKTHROUGH.md

Progressive disclosure: 200 tools and two skills ¶

A server with 200 tools sends all 200 in tools/list, and a client puts every schema into the model’s context. This walkthrough counts those bytes on a fixture server, then loads a skill, which a client reads only when the model needs it.

What you’ll learn ¶

  • tools/list returns all 200 tools - The tools come in eight themes: billing, deploy, search, users, storage, metrics, alerts and docs. A model that needs one billing tool still receives all 200 schemas. The host sends that many bytes to the model before the model does anything.
  • skills/list names the skills without their bodies - A skill is a SKILL.md with instructions, served under skill://. The listing carries each skill’s name, description and file digests. The host reads a body only when the model picks that skill.
  • Read billing-refunds and verify its digest - ReadFromEntry checks the served bytes against the size and digest from the listing before the host uses them. The skill names the billing tools it needs. A groups-aware server makes that link explicit.

Steps ¶

Setup ¶

Start the server in a separate terminal first:

Terminal 1:  just serve         # 200 tools + 2 skills on :8080
Terminal 2:  just demo          # this walkthrough (--tui for the interactive TUI)

Both sides take --wire=legacy or --wire=stateless. The results are the same on either wire.

Step 1: Connect ¶

Step 2: tools/list returns all 200 tools ¶

The tools come in eight themes: billing, deploy, search, users, storage, metrics, alerts and docs. A model that needs one billing tool still receives all 200 schemas. The host sends that many bytes to the model before the model does anything.

Step 3: skills/list names the skills without their bodies ¶

A skill is a SKILL.md with instructions, served under skill://. The listing carries each skill’s name, description and file digests. The host reads a body only when the model picks that skill.

Step 4: Read billing-refunds and verify its digest ¶

ReadFromEntry checks the served bytes against the size and digest from the listing before the host uses them. The skill names the billing tools it needs. A groups-aware server makes that link explicit.

Where groups fit ¶

The Progressive Disclosure working group drafts a groups extension, io.modelcontextprotocol/groups. A server that serves it shows one name and description per theme in groups/list. The client calls groups/get when the model picks a theme, and only then sees that theme’s tools and skills. mcpkit does not serve groups yet. A groups server would need themes and skill links, and this fixture already has both.

Where to look in the code ¶

  • Skills provider and client: ext/skills/provider.go, ext/skills/client_methods.go

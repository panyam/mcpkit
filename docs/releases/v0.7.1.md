# v0.7.1

A patch release for `ext/tasks`. A task can now report progress through
`statusMessage`, and a status update that races `tasks/cancel` can no longer
turn a cancelled task into a completed one. The rest is release tooling and
skills documentation. No protocol changes and no breaking API changes.

## Added

- **`ext/tasks`: `TaskContext.SetStatusMessage(msg)`.** SEP-2663 forbids
  `notifications/progress` on a task and says to report progress through
  `statusMessage`, but `TaskContext` had no way to set it. `SetStatus` changes
  only the status, and the task store is private to the runtime, so a server
  had to create the store itself, keep a handle on it, write the field, and
  build the `notifications/tasks` payload by hand. slyds did exactly that for
  its per-slide `analyze_deck` task.

  `SetStatusMessage` sets `statusMessage` and sends `notifications/tasks`,
  leaving the status alone:

  ```go
  for i, item := range items {
      tc.SetStatusMessage(fmt.Sprintf("Processing %d/%d", i+1, len(items)))
      // ...
  }
  ```

  (PR 1490)

## Fixed

- **`ext/tasks`: a status update can no longer revive a finished task.**
  `TaskStore.Update` has no terminal guard; only `StoreTerminalResult` has one.
  A `SetStatus(TaskWorking)` that landed after `tasks/cancel` moved the task
  back to `working`, and when the handler returned, its result was stored over
  the cancellation. The client then saw a task it had cancelled report
  `completed`.

  `SetStatus` and `SetStatusMessage` now return `tasks.ErrTaskTerminal` and
  change nothing once the task has completed, failed or been cancelled. The
  `input_required` transitions inside `TaskElicit` and `TaskSample` go through
  the same check. One of them carried a comment claiming the store already
  rejected the write, which it did not. Every update now also stamps
  `lastUpdatedAt`, which `SetStatus` never did. (PR 1490)

  Behaviour change for callers: `SetStatus` on a terminal task used to return
  nil after overwriting the status. It now returns `ErrTaskTerminal`. That
  write could only corrupt a finished task, so a loop can treat the error as a
  signal to stop.

- **`ext/skills` doc comments describe `skills/list`.** Comments still
  described `skill://index.json` reads and the `Index` / `IndexEntry` /
  `ReadSkillFileVerified` API removed in v0.6.0. `WithListCacheHints` claimed
  `ttlMs` is omitted without a cache TTL, when the code falls back to
  `DefaultListTTLMs` and always sends it. `WithSupportingFileDigests` and
  `ErrSupportingFileUnpinned` are now documented as having no effect, since
  every listed file carries a digest.

- **The skills walkthrough narrates `skills/list` and `skills/get`.** Its run
  blocks moved off the retired index in v0.6.0 and the narration did not. The
  archive digest step also never set its expected digest and always printed a
  mismatch; it now compares against the real value. (PR 1489)

## Changed

- **`make bump-root` repoints sibling pins in tagged modules**, not only the
  root require. v0.7.0 needed hand edits for this. `scripts/bump-pins.sh`
  moves every intra-repo pin in a tagged module to the release version, leaves
  `v0.0.0` placeholders and untagged examples alone, and has a fixture
  self-test in CI. This is the first release cut with it. (PR 1489)
- **`make audit` fails on a gitleaks finding.** The recipe used to swallow
  every gitleaks exit as "not installed", so a real finding read as a missing
  tool. It now skips only when the binary is absent. `.gitleaks.toml`
  allowlists the one synthetic Standard Webhooks test secret by exact value.
  (PR 1489)
- Two `ext/auth` table tests stopped copying token sources that hold a
  `sync.Mutex`, which `go vet` flagged. (PR 1489)

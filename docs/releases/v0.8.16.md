# v0.8.16

A patch release for clients that launch stdio servers. A command transport can start its server
with a clean environment. A client can reconnect after a transient failure without re-sending the
request that hit it. A server that exits mid-request is now a transient failure. And a reconnect
declares the client's real capabilities instead of none. chakra's stdio MCP servers (chakra issue
161) need all four.

## Added

- **`client.WithCleanEnv()`**, a `CommandOption`. The subprocess starts from an empty environment,
  so it sees only the variables given with `WithEnv` rather than everything the client process has.
  Nothing is added implicitly, not even `PATH` or `HOME`. (PR 1656)
- **`client.WithReconnectWithoutReplay()`**. With `WithMaxRetries` set, a transient failure still
  reconnects (for a command transport, a fresh process), but the request that failed comes back
  failed instead of being sent again. A request that failed in flight may already have run on a
  server that then died, so replaying it can run a tool twice. Notifications are still replayed.
  (PR 1656)

## Fixed

- **A reconnect dropped the client's capabilities.** The re-initialize after a transient failure
  declared an empty `ClientCapabilities`, so the server reached again no longer knew the client
  took roots, elicitation or sampling. It now declares what `Connect` does. (PR 1656)
- **A stdio server that exited mid-request wasn't a transient error.** The pending call failed with
  `stdio transport closed`, which `IsTransientError` didn't match, so a crashed command server was
  never reconnected. The error now wraps `io.ErrUnexpectedEOF`. (PR 1656)

Also in this range: dependabot bumps to the rooms TypeScript client and the React apps example
(PRs 1654, 1655).

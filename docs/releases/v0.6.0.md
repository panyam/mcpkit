# v0.6.0

A minor release, and the first cut since v0.5.2 on 2026-08-21. Thirty-seven PRs
landed in that window, so this consolidates roughly a month of work.

The bump is a minor rather than a patch because three tagged modules break API.
SEP-2640 moved from a served `index.json` to `skills/list` and `skills/get`, and
`ext/skills` deleted the old surface rather than carrying both. The Events
extension corrected two duration fields it had been emitting against the spec
for four months. The agents extension stopped claiming a spec namespace no SEP
defines. Each is covered below with before and after values.

The other reason to read this one: **a middleware bypass on the SEP-2575
stateless wire is fixed**. `resources/read` did not run the middleware chain, so
an authorization gate applied to tools and prompts and silently did not apply to
resource reads. If you run the stateless wire with a scope gate, this is the
entry that matters.

The agent SDK is also gone from the tree, extracted to
[chakra](https://github.com/panyam/chakra). That removal is not a breaking
change for anyone: those modules were never in `SUB_MODS_TO_TAG` and were never
tagged. See `VERSIONING.md` § Agent SDK.

## Breaking

- **`ext/skills`: `skill://index.json` and everything serving it is deleted.**
  The 2026-08-21 SEP-2640 revision retired the index in favour of two methods,
  and this release follows it rather than shipping both. Removed exports:
  `IndexURI`, `IndexPath`, `IndexSchemaURI`, `IsIndexURI`, `IndexResourceDef`,
  `Index`, `IndexEntry`, `NewIndex`, `SkillType` and its two constants,
  `MetaKeyFileDigests`, `FileDigest`, `Provider.Catalog`, `Client.ListSkills`,
  `Client.ReadSkillFileVerified`, and `WithoutIndex`.

  *Migration:* enumerate with `skills/list` and fetch with `skills/get`, both
  added in this release. `Client.ListSkills` becomes the `skills/list` call;
  `ReadSkillFileVerified` is superseded by the `resources` manifest on each
  entry, which pins `SKILL.md` and every supporting file under one verification
  rule instead of two.

  `WithoutIndex` has no replacement by design. Declaring the extension commits a
  server to both methods, so suppressing them while still declaring would be
  non-conformant. A server that will not enumerate returns an empty listing.

  Two things carried across rather than being dropped: the `_meta` version
  counter moved onto the `skills/list` result, since losing it would have been a
  silent regression for stateless pollers, and archives keep their packing code
  and every traversal, symlink and bomb guard. Only the listing-entry
  discriminator went, the SEP having deferred archives to an appendix. (PR 1344)

- **`experimental/ext/events`: two duration fields were wrong and are renamed.**
  Spec commit `197c32b4` renamed the duration fields to an `Ms` suffix in
  2026-05. mcpkit followed it for `ttlMs` and not for the other two, so it
  shipped the pre-rename names for four months against a spec that said
  otherwise. `wire_shape_test.go` asserted the old name, which is why CI stayed
  green throughout.

  | | Was | Now |
  |---|---|---|
  | wire | `nextPollSeconds: 5` | `nextPollMs: 5000` |
  | wire | `maxAge` (seconds) | `maxAgeMs` (milliseconds) |
  | Go | `MaxAgeSeconds` | `MaxAgeMs` |

  `maxAgeMs` changes across `events/poll`, `events/subscribe` and
  `events/stream`, including the replay-floor arithmetic and both client SDKs.
  The Go rename lands on `RegisterParams`, `WebhookTarget` and the GORM row, so
  the unit in the name matches the unit in the field.

  *Migration:* multiply existing second values by 1000. `EventDef` also gains an
  optional `InputSchema`, which the spec has required on `events/list` since its
  first revision. (PR 1379)

- **`experimental/ext/agents`: the extension ID moved to a vendor namespace.**
  `io.modelcontextprotocol/agents` becomes `io.mcpkit/agents`. The primitive was
  claiming the spec namespace for something no SEP defines, while the working
  group has not chosen among three candidate wire shapes.

  Matching the name while the shape is unsettled is the worse failure mode: a
  client recognising the standard identifier negotiates it and then receives a
  payload the eventual spec does not describe. A client that does not recognise
  `io.mcpkit/agents` skips the primitive, which is correct for an unratified
  surface.

  *Migration:* update the identifier your client negotiates. Everything in the
  tree referenced `ExtensionID` symbolically, so the change is one constant.
  This moves back to `io.modelcontextprotocol/` when a SEP lands **and** matches
  the ratified shape, not merely when the name is known. (PR 1341)

## Fixed

- **Middleware bypass on the stateless wire: `resources/read` now runs the
  chain.** `handleToolsCall` and `handlePromptsGet` both routed through
  `Backend.InvokeWithMiddleware`; `handleResourcesRead` did not, and
  `InvokeWithMiddleware`'s terminal switch had no `resources/read` case either.

  This affected any middleware, not only authorization: a rate limiter or an
  audit hook applied to tools and prompts and did not apply to resource reads.
  Where the middleware is an authorization gate it is a bypass rather than a
  missing feature, since a caller refused a tool could ask for the resource
  instead. The session wire was never affected.

  The same change completes template matching on this wire, which the handler
  had acknowledged as unfinished. Templated resources returned `-32602 unknown
  resource` on the stateless wire while working on the session wire. Resolution
  now mirrors the session dispatcher, exact URIs before templates in
  registration order, so a URI resolves to the same definition whichever wire it
  arrives on. Found by running mcpkit against the upstream SEP-2350
  scope-challenge scenario. (PR 1352)

- **Extension settings are inlined, per SEP-2133 (Final).** The spec maps an
  extension identifier straight to its settings object; mcpkit wrapped those
  settings in an `{id, specVersion, stability, config}` envelope of its own,
  putting every setting one level below where the spec puts it. A conformant
  client reading `extensions[id].directoryRead` found nothing, so
  `resources/directory/read` support was served but invisible.

  The conformance suite scored that as six SKIPPED checks rather than a failure,
  because a server that has not declared the flag need not serve the method, so
  the directory scenario reported 1/1 passed while exercising none of the
  surface. It now runs 7/7. `core.ExtensionCapability` becomes
  `map[string]any`, modelling the wire directly. (PR 1337)

- **`ext/skills` accepts any URI scheme again.** `ParseURI` required the scheme
  be exactly `skill`, and it sits on the live client path, so a server serving a
  conforming catalog under a domain-native scheme was refused outright. SEP-2640
  says the opposite in as many words, and mcpkit's own conformance check already
  graded it a WARNING: the client was stricter than the suite. The parser also
  stopped rewriting the scheme it parsed. (PR 1369)

## Added

- **SEP-2640 skills: `skills/list` and `skills/get`.** Both methods per the
  2026-08-21 revision, plus the entry shape they carry. `SkillEntry` is
  `{uri, frontmatter, resources}`, where frontmatter is the verbatim block
  rather than a hoisted name and description, because the SEP requires a host to
  compare the entry field-by-field against the `SKILL.md` it later fetches and a
  flattened struct cannot represent keys it does not name. `resources` is a
  complete `{uri, digest, size}` manifest or the `dynamic` sentinel. (PRs 1342,
  1343)

- **Nested skills are permitted**, per the 2026-08-21 SEP-2640 reversal.
  Resource registration goes to the innermost owning skill, so one file is one
  URI served once, while the entry manifest keeps walking the whole subtree. A
  file therefore appears in two manifests and at one URI, which is the SEP's
  completeness rule rather than a workaround for it. (PRs 1337, 1345)

- **`skills/get` carries cache attributes.** The stable spec page merged
  `GetSkillResult extends CacheableResult`, making `ttlMs` and `cacheScope`
  REQUIRED as they are on `resources/read`. Worth recording as a behaviour
  change rather than a clarification: SEP-2640 leaves the question open, so a
  server conformant to the SEP text alone omits both and becomes non-conformant
  to the page. mcpkit follows the page, which is what the conformance suite
  grades against. (PR 1372)

- **Skills gain frontmatter verification, size checks and server page-size
  options**, plus a cursor-following directory read and conformance drivers for
  the SEP-2640 client scenarios. (PRs 1343, 1367)

- **Request-time scope challenges across all primitives.** Scope gating was
  tools-only and fixed at registration time; both limits lift.
  `core.ScopeChallengeFunc` decides per request and receives the request, so the
  answer can depend on the arguments rather than only on which primitive was
  addressed. That is the case that matters in practice: GitHub's MCP server
  needs the workflow scope only when a commit touches `.github/workflows`, and
  needs repo-admin or org-admin depending on the target the arguments name.

  The field is on `ToolDef`, `ResourceDef`, `ResourceTemplate` and `PromptDef`,
  and `NewScopeMiddleware` gates `tools/call`, `resources/read` (exact and
  templated) and `prompts/get`. `core.RequireScopes` and `core.AcceptAnyScope`
  keep the static cases to one line.

  **Nothing changes for an existing server.** `RequiredScopes` and
  `AcceptedScopes` are deprecated but fully honoured when `ScopeChallenge` is
  nil, including the OR-hierarchy semantics and the least-privilege
  advertisement, and adding the middleware gates nothing until a definition opts
  in. They go once the upstream design settles; `typescript-sdk#1624` has been
  rewritten twice in ten days, so chasing it now risks breaking users twice.
  `JWTValidator.ScopeExtractor` covers the other axis of provider variation.
  (PR 1353)

- **Events: `list_changed` and termination on event-type removal**, per spec
  commit `28ec35e9`. (PR 1381)

- **The events stack publishes as one self-contained compose** (issue 1373,
  committed directly to main), with follow-up fixes to the auth profile, the
  stateless wire and nginx interpolation. (PRs 1385, 1389, 1390)

## Changed

- **The agent SDK left the repository**, extracted to
  [chakra](https://github.com/panyam/chakra), which consumes mcpkit as an
  ordinary dependency. The dependency runs one way and
  `scripts/verify-submodule-deps.sh` enforces it. Not a breaking change for
  consumers: those modules were never tagged. The old `agent/vX.Y.Z` tags are
  not retracted and stay resolvable forever, since module proxy content is
  immutable. (PR 1337)

- **Conformance suites now grade mcpkit.** `testconf-tasks-v2` and
  `testconf-mrtr` reported PASS for months while scoring upstream's own
  TypeScript reference server: they exported `TASKS_SERVER_URL` /
  `MRTR_SERVER_URL` and ran an upstream vitest file that reads neither and
  spawns its own server. Both are now CLI-driven per scenario. Suite runs also
  report the upstream worktree SHA and warn when it is behind. (PRs 1358, 1359,
  1383)

- **New conformance coverage:** `testconf-events` against the draft Events suite
  (INFO, red on purpose), `testconf-skills` retargeted to upstream `main` and
  gated, and the SEP-2350 scope-challenge suite tracked at 17/17. Server
  tier-check moves 30/30 to 31/31. (PRs 1354, 1377, 1378)

- **CI and build hygiene:** example modules that replace out of the repo are
  skipped, every example is gated on compiling, the Pages coverage step's
  failures are readable, the conformance report renderer moved to pnpm, and two
  stale dependency-baseline entries are dropped. (PRs 1338, 1340)

- **Prose sweep** across the documentation corpus, plus corrected stale doc
  comments and handler-signature examples in `core`. (PR 1339)

- **Dependency updates** across Go and npm module groups, including
  `google.golang.org/grpc` to v1.83.2 and several GitHub Actions majors.

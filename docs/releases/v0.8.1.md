# v0.8.1

A patch release with two parts. mcpkit gains opt-in DPoP (RFC 9449, SEP-1932)
on both the client and the server. oneauth moves to v0.2.2, which fixes two
security issues. Nothing changes for a deployment that does not configure
DPoP, and there are no breaking API changes.

## Security

- **oneauth v0.2.2** in every module that uses it. It fixes two issues
  (oneauth issue 434):
  - Its HTTP introspection endpoint never returned `cnf`. A resource server
    validating through `POST /oauth/introspect` could not see a token's DPoP
    binding, so it accepted a bound token presented as Bearer. Every oneauth
    version since 0.1.37 is affected.
  - Under `FAPI2`, a jwt-bearer or token-exchange request with no client
    authentication was issued a token.

  mcpkit's own validators were not exposed. `JWTValidator` reads `cnf` from
  the JWT itself, and `IntrospectionValidator` does not do DPoP yet. The bump
  matters for anyone who runs oneauth's authorization server alongside
  mcpkit. (PR 1559)

## Added

- **DPoP, opt-in, on both sides.** SEP-1932 is still a draft, and the auth WG
  has not chosen between DPoP, mTLS and HTTP message signatures, so this is
  off unless configured. oneauth does the cryptography and mcpkit wires it in.
  (PR 1557, issue 803)

  On the client, give `OAuthTokenSource` a key:

  ```go
  key, _ := oneauthclient.NewDPoPKey()
  ts := &auth.OAuthTokenSource{ServerURL: serverURL, DPoPKey: key}
  ```

  The authorization request carries `dpop_jkt`, the token and refresh
  requests carry proofs, and each MCP request presents the token as
  `Authorization: DPoP` with a fresh proof. If the MCP server answers
  `use_dpop_nonce`, the transport retries once with the nonce. The hook is the
  new `core.ProofTokenSource`, so any token source can opt in.

  On the server, give `JWTValidator` a proof validator:

  ```go
  v := auth.NewJWTValidator(auth.JWTConfig{
      // ...
      DPoP: apiauth.NewDPoPProofValidator(apiauth.DPoPConfig{BaseURL: "https://mcp.example.com"}),
  })
  ```

  It checks every request's proof against the token's `cnf.jkt`, cache hits
  included, and refuses a bound token presented as Bearer. `RequireDPoP`
  refuses Bearer outright. Failures are `DPoP` challenges, and a nonce
  challenge carries `DPoP-Nonce` through the new `core.AuthResponseHeaders`.
  `MountAuth` advertises `dpop_signing_alg_values_supported` in Protected
  Resource Metadata.

  Upstream client conformance is now 43/43 (581 checks, 0 failed).
  `auth/dpop` and `auth/dpop-nonce` were the last expected failures.

  Not covered yet: `IntrospectionValidator` and the scope middleware, and the
  client-credentials, JWT-bearer and enterprise-managed token sources. The
  server side is graded by mcpkit's unit tests until upstream's server suite
  (conformance PR 395) merges.

## Changed

- **oneauth v0.2.0, then v0.2.1.** v0.2.0 rolls up the DPoP, FAPI 2.0 and
  security-audit work. v0.2.1 adds `DPoPKey.ProofWithNonce`, which the
  client's nonce retry uses. (PRs 1556, 1557)
